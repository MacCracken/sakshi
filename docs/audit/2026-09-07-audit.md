## HIGH

### SK-2026-01: TSC calibration fails silently on coarse-clock hosts — every timestamp is 0, and every call re-enters the 10 ms window

**File**: `src/clock.cyr` (`_sk_clock_init`, `_sk_now_ns`)
**Severity**: HIGH
**Status**: **FIXED in 2.5.0**

`_sk_clock_init` calibrated the TSC by sampling a reference clock across a single
10 ms `nanosleep` window and computing `freq = dt * 1e9 / dn`. It wrote the
frequency only `if (dn > 0)`.

On Windows PE, `_sk_clock_now_ns_raw` is `GetTickCount64`, whose tick is
**~15.6 ms**. Both ends of a single 10 ms window therefore routinely land inside
one tick, giving `dn == 0`. No frequency, no scale — and `_sk_ticks_to_ns` then
multiplies the cycle counter by a **zero** scale, so every timestamp is `0`.

**Observed deterministically**: the PE smoke printed `[0] [INFO] sakshi smoke ok`
on **5 of 5** cold runs under wine before the fix, and a real monotonic timestamp
on 5 of 5 after.

The second half is worse than the wrong value. The two guards disagreed about
what "initialized" means:

- `_sk_now_ns` re-entered init whenever `_sk_tsc_scale == 0`
- `_sk_clock_init` early-returned whenever `_sk_tsc_freq_hz > 0`

When calibration fails both stay `0`, so the early return never fires and **every
single `_sk_now_ns` call runs the full calibration path — including a 10 ms
`nanosleep`**. On a host whose reference clock never advances, a logging library
stalls its caller for 10 ms per emitted event.

**Failure scenario**: a Windows consumer calls `sakshi_info` in a request handler.
The first event carries timestamp 0, so span elapsed times and event ordering
against it are meaningless. If `GetTickCount64` is stuck (suspended VM, broken
timer), every subsequent log call sleeps 10 ms and throughput collapses to
100 events/second.

**Fix**:
1. Retry the calibration window up to 8 times, requiring `dn > 0 && dt > 0`. Each
   retry adds 10 ms of separation, so a coarse tick is crossed within a couple of
   attempts. Bounded, so a dead clock costs a fixed 80 ms **once**.
2. New `_sk_clock_init_done` flag — one variable, one meaning ("we already
   tried"), set on every exit path including the AGNOS early return. `_sk_now_ns`
   now gates on it, so init cannot be re-entered.
3. If the scale is still 0 after init, `_sk_now_ns` falls back to
   `_sk_clock_now_ns_raw()` — coarse, but monotonic and non-zero.
4. `sakshi_clock_recalibrate` clears the new flag, or it would have become a
   silent no-op.

This also closes the remaining half of **SA-010**: the Windows branch of
`_sk_clock_now_ns_raw` still does not check its return, but a failed reading now
degrades to the fallback path instead of producing a zero scale.

**Regression test**: `tests/tcyr/sakshi.tcyr` — "clock: calibration-failure
fallback" forces the failed-calibration state portably and asserts a non-zero,
monotonic timestamp plus non-re-entry. Verified to **fail** without the fix.

## MEDIUM

### SK-2026-02: ring writer did not clamp `msg_len` — oversized events overwrite their own header and desync the ring

**File**: `src/output.cyr` (`_sk_write_ring_event`)
**Severity**: MEDIUM
**Status**: **FIXED in 2.5.0**

Of the three binary writers, `_sk_write_ring_event` was the only one that wrote
the caller's `msg_len` straight into the 12-byte header and then copied that many
bytes. `_sk_write_aring_event` and `_sk_write_udp_event` both clamp to 256 first,
and the 2026-04-15 audit's **SA-001** fixed exactly this shape in the UDP header —
the ring path was never given the same treatment.

Two silent failure modes:

- **`msg_len >= 65536`** — `store16` keeps only the low 16 bits, so the header
  advertised `msg_len & 0xFFFF` while the loop wrote the **full** `msg_len` bytes.
  Every later decode resumes mid-event; the rest of the ring is garbage.
- **`4085 <= msg_len <= 65535`** — the header is accurate but names an event
  larger than the 4096-byte ring, so `sakshi_ring_decode_event` rejects it via its
  own `msg_len > 4084` guard and the ring is undecodable from that point on.

**Failure scenario, as actually observed in the new test**: log a 5000-byte
message with `SK_OUT_BUFFER` active. The event is 5012 bytes into a 4096-byte
ring, so it **wraps and overwrites its own header**. Reading the header back
yields `16705` — `0x4141`, two bytes of the message payload — instead of any
length the writer intended. The decoder then returns 0 and the whole ring is lost.

Masked indexing (`& 0xFFF`) means this never writes outside `_sk_ring_buf`, so it
is data-integrity loss, not memory corruption — hence MEDIUM, not HIGH.

**CVE pattern**: same class as [CVE-2026-31694](https://nvd.nist.gov/vuln/detail/CVE-2026-31694)
(Linux FUSE) — a serialized entry copied into a fixed-size buffer without first
validating that it fits.

**Fix**: clamp to `4084` (= 4096 ring − 12 header) before the header is written,
and copy the clamped length. 4084 rather than 256 is deliberate: it is exactly
what the decoder accepts, so every message that decodes correctly today still
does. Negative lengths clamp to 0.

**Regression test**: "ring buffer oversized message is clamped, not desynced".
Verified to fail (4 assertions) without the clamp.

### SK-2026-03: selecting an unconfigured output target silently discards every event

**File**: `src/output.cyr` (`sakshi_set_output`)
**Severity**: MEDIUM
**Status**: **FIXED in 2.5.0**

`sakshi_set_output(target)` assigned `_sk_output_target` unconditionally and
returned 0. Selecting a target that was never set up left the library in a state
where every subsequent event is discarded with no diagnostic anywhere:

- `SK_OUT_FILE` with no `sakshi_output_file()` → `_sk_file_fd == -1` →
  `_sk_write_file` returns without writing
- `SK_OUT_UDP` with no `sakshi_output_udp()` → `_sk_udp_fd < 0` →
  `_sk_write_udp_event` returns immediately
- `SK_OUT_HOOK` with no `sakshi_set_emit_hook()` → `_sk_emit_hook == 0` → dropped

**Failure scenario**: a consumer calls `sakshi_set_output(SK_OUT_FILE)` and only
later (or never, on an error path) calls `sakshi_output_file`. Logging appears
configured and produces nothing. Nothing in the API reports it.

This is the same defect class the 2.4.x line already fixed twice — the full span
stack (`span.cyr`) and the truncating `sakshi_log_kv` scratch (`trace.cyr`) — on
the stated principle that a tracing library that stops tracing has to say so.

**Fix**: return a non-zero diagnostic (`-1` file, `-2` UDP, `-3` hook, `-4`
unknown target) while still honouring the switch. Purely additive: every existing
caller ignores the return and behaviour is unchanged.

**Regression test**: "set_output reports an unconfigured target", 8 assertions.

### SK-2026-06: macOS decoded the monotonic clock from the wrong place — garbage TSC calibration

**File**: `src/clock.cyr` (`_sk_clock_now_ns_raw`)
**Severity**: HIGH
**Status**: **FIXED in 2.5.0**

`_sk_clock_now_ns_raw` had a `CYRIUS_TARGET_WIN` branch and a Linux branch, and
nothing else — so macOS fell through to the **Linux** path and decoded
`load64(&ts) * 1e9 + load64(&ts + 8)` out of the timespec buffer.

That is the wrong place on Darwin. `syscall(228, 4, _)` **is** rerouted on both
Mach-O backends — `EMACHO_CLOCK_ARM` to libSystem
`_clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW=4)` via `__got[6]` on arm64,
`EMACHO_CLOCK_X86` on x86_64 — and both return u64 nanoseconds **in the return
register**. Confirmed against cyrius's own reference consumer,
`_prof_clock_ns` in `src/backend/common/runtime.cyr`, which does exactly
`return syscall(228, 4, &ts);` for macOS and reserves the timespec decode for
Linux.

An in-tree comment claiming "x86-macOS is HELD — 228 is unrouted on x86-macho"
is what justified the omission; `runtime.cyr:310` documents the reroute and its
`mov rax,[rdi]` dereference, so that comment was stale.

**Failure scenario**: on any macOS build the calibration anchors are read out of
a buffer the reroute never filled as a timespec, so `dn` is meaningless, the
computed TSC frequency is wrong, and every timestamp and every
`sakshi_span_exit` elapsed value is wrong by whatever factor that garbage
produced. Not detectable from inside sakshi — the numbers look plausible.

**Fix**: a `CYRIUS_TARGET_MACOS` branch returning the syscall result directly.
The buffer is still passed as a real address because `EMACHO_CLOCK_X86`
dereferences the third argument — cyrius v6.5.43 SIGSEGV'd on Intel Mac for
passing a literal `0` there.

**Not covered by CI**: there is no macOS lane. This was found by reading the
toolchain's translation tables, and is verified against them rather than by
execution.

### SK-2026-07: macOS UDP reported success and then sent nothing

**File**: `src/output.cyr` (`sakshi_output_udp`, `_sk_write_udp_event`)
**Severity**: HIGH
**Status**: **FIXED in 2.5.0**

The Mach-O `ESYSXLAT` table (`src/backend/aarch64/emit.cyr`) translates
`socket` — entry `41 → 97` — but has **no entry for `sendto`**, neither the x86
`44` nor the aarch64 `206`. Verified by enumerating every `_esx_arm` entry in
the table.

That asymmetry is worse than a missing pair. The `socket` call succeeds and
returns a real fd, so `sakshi_output_udp` set `_sk_udp_fd`, flipped the target
to `SK_OUT_UDP` and **returned success** — after which every event issued an
untranslated syscall number: silently emitting nothing on arm64, and on x86
running an unrelated BSD call or taking SIGSYS.

**Fix**: refuse up front with `-1` on macOS, exactly as the AGNOS branch already
does, so the caller keeps its working stderr/file target; and exclude the
`sendto` call site. Header comment now lists macOS beside Windows PE.

### SK-2026-08: a wrapped ring decoded caller payload as an event header

**File**: `src/output.cyr` (`sakshi_ring_decode_event`)
**Severity**: MEDIUM
**Status**: **FIXED in 2.5.0**

`sakshi_ring_read_raw` computes `start = _sk_ring_write - avail`, which once the
ring has wrapped lands **mid-event**. The first 12 bytes handed to the decoder
are therefore message payload — caller data — not a header, and the decoder
parsed them as one.

This needs no attacker: any long-running consumer wraps the 4096-byte ring, and
from then on the flight recorder is unreadable precisely in the situation it
exists for. **No test covered a wrapped ring** — the existing ring tests write
about 60 bytes.

It also admits log forgery. A consumer that logs attacker-influenced bytes
(`sakshi_warn(user_agent, n)`) lets an attacker embed a well-formed 12-byte
header inside their own message; once the ring wraps onto it the decoder emits
attacker-chosen text as a `FATAL` line with an attacker-chosen timestamp.

**Fix**: validate `level` against the exact set `_sk_level_str` knows (0–5,
10, 11, 255) before decoding. A misparse becomes a caller-visible "cannot
decode" instead of a fabricated log line. Note the ceiling guard alone was not
enough: a forged header with `msg_len = 4` passes it.

**Regression test**: "decode rejects a plausible-looking header with an
impossible level" — verified to fail without the guard (it decoded 25 bytes of
caller data as a log line). Plus a wrapped-ring test that fills and wraps the
ring twice over.

### SK-2026-09: `_sk_fmt_int` ran two divisions per digit

**File**: `src/format.cyr`
**Severity**: LOW (performance)
**Status**: **FIXED in 2.5.0**

The digit loop was `d = n % 10; ... n = n / 10;` — two 64-bit `idiv` per digit.
A nanosecond timestamp is 14+ digits, on the text hot path, and `_sk_fmt_span`
formats two integers per EXIT line.

Replaced with one division per digit: `q = n / 10; d = n - q * 10; n = q`. Both
`/` and `%` truncate toward zero, so this is exactly `n % 10` for every i64
including negatives, and the 2.4.8 i64::MIN negate-the-digit fix is preserved.

Measured end-to-end over 4 runs each (1e6 iterations):

| Benchmark | before | after | delta |
|---|---|---|---|
| `trace_info` | 598 ns | 580 ns | **−3.0%** |
| `span_cycle` | 1.168 µs | 1.127 µs | **−3.5%** |

Binary targets are unchanged, as expected — they format no integers.

### SK-2026-10: re-opening a file or UDP target leaked the previous descriptor

**File**: `src/output.cyr`
**Severity**: LOW
**Status**: **FIXED in 2.5.0**

`sakshi_output_file` and `sakshi_output_udp` overwrote `_sk_file_fd` /
`_sk_udp_fd` without closing what was there. A log-rotating consumer leaks one
descriptor per rotation until it hits `RLIMIT_NOFILE`, at which point `_sk_open`
starts failing and logging stops. Both now close the previous fd first.

### SK-2026-11: only the upper bound was clamped on two binary writers

**File**: `src/output.cyr`
**Severity**: LOW
**Status**: **FIXED in 2.5.0**

`_sk_write_aring_event` and `_sk_write_udp_event` clamped `msg_len` from above
but not below. In the atomic ring that matters most: `event_size = 12 + m_len`
feeds `atomic_fetch_add` on the **shared reservation cursor**, so a negative
length moves that cursor backwards and breaks the disjointness the whole
multi-producer design rests on — every later reservation would overlap live
data. Both now clamp at 0.

### SK-2026-12: `sakshi_span_exit` guarded only one end of the span stack

**File**: `src/span.cyr`
**Severity**: LOW (defense-in-depth)
**Status**: **FIXED in 2.5.0**

`sakshi_span_enter` clamps a negative depth and rejects `>= 16`;
`sakshi_span_exit` checked only `<= 0` and then indexed at `(depth-1)*24` with
no upper bound. A depth of 17 gives offset 384 — one entry past the 384-byte
stack — and the three loads would take a name pointer and length from the
globals that follow it and hand them to the formatter to dereference.

The verify pass **correctly refuted this as a reachable bug**: depth is written
in exactly two guarded places and nothing else can raise it above 16
single-threaded. It is fixed anyway as the mirror of the lower-bound guard added
in 2.4.12, on that release's own stated reasoning — memory corruption elsewhere,
or a contract violation the library cannot enforce.

## Addendum — 2.5.1: both deferred findings resolved

Both were re-examined against primary sources and both turned out to be
**sakshi's**, so neither was filed against AGNOS. One has an upstream twin that
was filed against cyrius.

**AGNOS `uptime_ms` frozen — CONFIRMED, fixed in 2.5.1.** Not speculative:
AGNOS's own userland ABI (`agnos/docs/development/agnos-userland-abi.md`, row 95)
states that a foreground `run` program starts with IF cleared, so the timer ISR
never fires and #40 is frozen for the program's whole run — and that this cost
two iron burns before it was understood. AGNOS supplies the correct syscall
(`uptime_us`#95, rdtsc-backed, returns -1 rather than a plausible 0 on refusal)
and documents #40's limitation, so **there is no AGNOS-side defect to file**.
sakshi now prefers #95 with a #40 fallback. Verified by disassembly that `95`
const-folds to an immediate in the `--agnos` build and appears zero times in the
x86_64 build, so the ifdef genuinely bars Linux's colliding `umask`.

**The same defect exists upstream in cyrius** — `lib/chrono.cyr:22` binds
`clock_now_ns()` on AGNOS to the same frozen #40, while
`lib/syscalls_x86_64_agnos.cyr:1202` in that same repo documents the trap and
says "#95 is the only correct clock there". Filed as
`cyrius/docs/development/issues/sakshi-agnos-chrono-uptime-ms-frozen-2026-09-07.md`.

**Atomic-ring aliasing — fixed in 2.5.1, partially.** The writer now detects that
its reservation was re-issued while it was preempted and drops rather than
writing through the newer event, at a measured +2.4 ns. The residual window
(being lapped *during* the byte loops) is documented in-source and carried to a
minor release; closing it needs per-slot generation stamps or a CAS commit
protocol, which change the layout or cursor semantics.

## Findings originally deferred (both since resolved — see addendum above)

**AGNOS `uptime_ms` (#40) may be frozen for a foreground ring-3 program**
(`clock.cyr`, MEDIUM). If true, every AGNOS timestamp is identical and every
span reports 0 ns. The suggested fix routes through AGNOS syscall #95, whose
contract could not be verified from this tree, and there is no AGNOS lane to
test against. Changing the only working clock on a platform on the strength of
an unverified syscall number is a worse risk than the bug. **Filed, not fixed.**

**Atomic-ring reservations alias in buffer space** (`output.cyr`, MEDIUM). Two
producers can write the same 4096-byte window if one is preempted between its
`atomic_fetch_add` and its byte loop while the other emits ~16 events. The
in-source comment claiming "a handful of in-flight reservations ... cannot alias
each other" is true only for a handful. The proposed lapped-reservation
detection is a real change to the one lock-free path in the library and wants
its own release with a concurrency test harness. **Filed, not fixed.**

## CVE / pattern review

Re-checked against the 2026-04-15 pattern table; sakshi's posture is unchanged
except where noted.

| Pattern | Sakshi status |
|---|---|
| **Log injection** (Log4Shell CVE-2021-44228) | Not vulnerable — no interpolation, no lookups, no format-string parsing. Messages are opaque byte ranges written verbatim. |

| **Ring buffer race** (CVE-2020-14386) | Single-threaded by contract; `SK_OUT_ATOMIC_RING` reserves disjoint ranges with `atomic_fetch_add`. A reader may still observe a reserved-but-unwritten newest event — documented in `output.cyr`, acceptable for the flight-recorder use case. |

| **Integer overflow in size fields** (CVE-2021-3156) | SA-001 fixed the UDP header in 2026-04; **SK-2026-02 closes the matching ring-header hole here.** |
| **Symlink/TOCTOU on file output** (CWE-367) | Unchanged — single `open` with `O_APPEND`, standard POSIX behaviour. `path` is documented as caller-trusted. |
| **Uninitialized memory disclosure** (CVE-2017-1000364) | Clean — the UDP packet buffer sends exactly `12 + clamped_len` bytes; no padding is transmitted. |

## Boundary contracts re-affirmed (not defects)

`sakshi_ring_read_raw(dst, max_len)` and `sakshi_aring_read_raw(dst, max_len)`
write up to `max_len` bytes to a caller-supplied pointer. The caller owns that
buffer's size, exactly as C's `read(2)` and `memcpy(3)` do. A negative `max_len`
yields a negative return and writes nothing. Documented, not changed.

`sakshi_output_file(path)` passes `path` to `open` without validation — the same
trust boundary as `fopen`. Path validation belongs to the consumer.
